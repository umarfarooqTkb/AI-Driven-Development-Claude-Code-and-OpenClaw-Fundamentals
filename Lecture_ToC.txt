** Undo or Rewind Changes in Claude Code and OpenCode ***
--------------------------------------------------------------------------------------------------------------------------------------------------------------
Both Claude Code and OpenCode provide features to restore an earlier conversation state and reverse code changes.

Claude Code:
Claude Code uses checkpointing. It automatically creates a checkpoint before each user prompt and tracks changes made through Claude’s file-editing tools.

Open the Rewind Menu
Use either:
/rewind
Or press:
Esc, Esc

Press the Esc key twice while the prompt input is empty.
If text is present in the prompt, pressing Esc twice clears the text instead of opening the rewind menu.

Rewind Options
After selecting a previous checkpoint, Claude Code provides the following options:
Restore code and conversation
Revert both the code changes and conversation to the selected checkpoint.
Restore conversation
Rewind the conversation while keeping the current code changes.
Restore code
Revert code changes while keeping the full conversation.
Summarize from here
Compress the conversation from the selected point onward to free context-window space.
Summarize up to here
Compress the earlier conversation while keeping the newer messages.
Important Limitations

Claude Code rewind does not necessarily restore:

Files changed through Bash commands such as rm, mv, cp, or shell redirection
Changes made by background subagents
Manual changes made outside Claude Code
Changes from another Claude Code session
Symlinked or hard-linked files

Therefore, Claude Code checkpointing should be treated as a session-level undo feature, not as a replacement for Git.


OpenCode

OpenCode provides the /undo command.

Undo the Last Interaction
/undo
This removes:
The most recent user message
OpenCode’s responses after that message
Associated file changes

It also restores the original prompt so that you can edit and submit it again.

You can run /undo multiple times to move further back through the conversation.


Keyboard Shortcut
Ctrl+X, then U


Redo an Undone Interaction
/redo
Keyboard shortcut:
Ctrl+X, then R
/redo restores the previously undone conversation and file changes.

Important Limitation
OpenCode uses Git internally to restore file changes. Therefore, the project should be inside a Git repository for reliable file restoration.


Simple Summary
Claude Code:
Esc + Esc → Select checkpoint → Restore code, conversation, or both
/rewind

OpenCode:
/undo
/redo

**** Prompt Caching: 
-------------------------------------------------------------------------------------------------------------------------------------------------

- A long and messy conversation does not only reduce the AI agent’s effectiveness; it can also increase token usage and cost.
- As a session grows, the request context may include:
  System instructions
  CLAUDE.md or AGENTS.md
  Previous user and assistant messages
  File contents
  Tool calls and tool results
  MCP tool definitions
  Compaction summaries

- when we send a message/prompt to AI and it responds to us.
- Every time we send message to AI, the whole previous conversation (context) also goes with it every time.
- It means every time cost is increasing with each message you send to AI. context is increasing and so the cost.
- In coding, relevant code base and all associated files are also going with the context, which is actually huge, which actually increases our cost too much.
- Coding agents normally send much of this context to the model again with each request. 
- Claude Code, for example, sends the conversation history with subsequent requests, including additional requests made during tool use.

- So LLM companies come up with a concept of Cache
- in this technique, they started to cache your context, if it is not changing
- Prompt caching makes repeated context cheaper, not free.

- Every cache is updated when you change something in rule files (CLAUDE.md or AGENTS.md), files, tools, context.
- Whenever cache is updated, whole cache will go with the next message, and a spike in cost is expected
- Also cache has some time, after that time, cache will be automatically cleared and new cache is stored, another spike in cost.


Cache Hit
-----------
- A cache hit happens when the beginning of the new request matches a previously cached prompt prefix.
Example:
- Previous request: A + B
- New request:      A + B + C
- A + B may be read from the cache.
- Only C is new input.
- Cached tokens may still be billed, but at the provider’s lower cache-read rate.

Cache Miss
-------------
- A cache miss happens when the provider cannot reuse some or all of the previous cached prefix.
Example:
- Previous request: A + B
- New request:      A + X

- A cache miss can happen when:
  The cache expires.
  CLAUDE.md, AGENTS.md or another instruction file changes.
  Tool or MCP definitions change.
  The selected model or provider changes.
  Thinking or reasoning settings change.
  Tool-choice configuration changes.
  Images or documents are added or removed.
  Earlier conversation history is edited, rewound, forked or reordered.
  A new session produces a differently structured prompt.


- Simply viewing or navigating the conversation does not necessarily break the cache. The cache is affected when the actual prompt sent to the provider changes.



Cache Lifetime
---------------------------------
- Cache lifetime depends on the provider and environment.
Examples:
- Anthropic API caching normally uses a five-minute lifetime.
- Anthropic also supports a paid one-hour cache.
- Current Claude subscription sessions use a one-hour cache lifetime.
- DeepSeek caching is automatic and best-effort; unused entries are generally cleared within several hours to several days.

- Claude Code and OpenCode are built to keep that front stable so the cache keeps working — but the caching itself is the provider's feature, and a model without it gets no discount. 
- The catch: the discount holds only while the front of the context stays unchanged.
- Edit your rules file, or jump around your history, and the cache resets from that point and you pay full price again. 



Cache Expiration
Prompt caches normally expire after a period of inactivity.
A successful cache hit may refresh the expiration timer.
After the cache expires, the next request may need to process and cache the input again.
This may cause the first request after a long break to be slower or more expensive.

Cache lifetime depends on the provider and authentication method.

Anthropic
The standard Anthropic API cache lifetime is normally five minutes.
A paid one-hour cache lifetime is also available.
Claude Code generally requests a one-hour cache lifetime for Claude subscription users.
When Claude Code uses an API key or supported third-party provider, the default is normally five minutes unless the one-hour option is enabled.
DeepSeek
DeepSeek context caching is enabled automatically.
It operates on a best-effort basis, so cache hits are not guaranteed.
Unused cache entries are generally cleared within a few hours to a few days.

hook and webhook
-------------------------------------------------------------------------------------------------------------------------------------------------
- The basic idea of a hook: A hook is a predefined point in a system where you can attach your own logic.
- In simple words:“When this stage or event happens, run my code.”

System event
    ↓
Hook is triggered
    ↓
Your custom code runs

Examples:
Before a file is saved, format it.
After a user logs in, record an audit log.
Before an API request is sent, add an authentication token.
After Claude Code uses a tool, run a validation script.

A hook normally works inside the same application or execution environment.


- Hooks can be defined at project level and global level.
- it is better that you should defin hooks on project level, as they are not become part of context, so hooks are not supplied in each request as part of context.
- so hooks does not cost any tokens.
- if you give command /context in claude code, you will not see the hooks in the output
- the reason is that, hooks are not part of LLM, they are linked with the tool.


Sample prompts:

2. General event hooks

Many tools use the term hook for lifecycle events.

For example:

Before action → Pre-hook
Action runs
After action  → Post-hook

Examples include:

Git hooks
Claude Code hooks
OpenCode plugin hooks
WordPress hooks
database hooks
CI/CD hooks
application lifecycle hooks
Git hook example
Developer runs git commit
        ↓
pre-commit hook runs
        ↓
Linting and tests execute
        ↓
Commit is allowed or blocked
Claude Code hook example
Claude Code attempts a command
        ↓
PreToolUse hook runs
        ↓
Security script checks the command
        ↓
Command is allowed or denied

These hooks are usually internal to the tool or local environment.




3. Webhooks

A webhook is an HTTP-based notification sent from one application to another application when an event occurs.

Application A
Event occurs
     ↓
HTTP POST request
     ↓
Application B webhook URL
     ↓
Application B processes the event

For example:

Customer completes Stripe payment
        ↓
Stripe sends an HTTP POST
        ↓
Your backend webhook endpoint receives it
        ↓
Your system marks the invoice as paid

A webhook usually includes JSON:

{
  "event": "payment.completed",
  "customerId": "12345",
  "amount": 100
}

The receiving application provides a URL such as:

https://api.example.com/webhooks/stripe

That URL is known as a webhook endpoint.




Hooks versus webhooks

| Area                  | Hook                                           | Webhook                                   |
| --------------------- | ---------------------------------------------- | ----------------------------------------- |
| Main purpose          | Attach logic to an event or lifecycle stage    | Notify another application about an event |
| Communication         | Usually internal or local                      | HTTP over a network                       |
| Applications involved | Usually one system                             | Usually two systems                       |
| Trigger               | Internal event                                 | Event in an external system               |
| Data format           | Function parameters, objects or standard input | Usually JSON in an HTTP request           |
| Example               | Run validation before saving                   | GitHub notifies your server about a push  |


The simplest distinction is:

Hook:
Something happened inside my system,
so run some code inside my system.

Webhook:
Something happened in another system,
so it sends an HTTP request to my system.
Their relationship

A webhook is conceptually a special network-based form of event callback.

Both follow the same general pattern:

Something happens
       ↓
Registered logic is triggered

But the location is different.

Hook
Application
├── Event happens
└── Internal hook function runs
Webhook
Application A
├── Event happens
└── Sends HTTP request
          ↓
Application B
└── Webhook endpoint runs

A hook can also call a webhook:

Claude Code finishes a task
        ↓
Stop hook runs
        ↓
Hook sends HTTP POST
        ↓
Microsoft Teams receives notification

In this example:

Stop is the hook.
The HTTP request is the webhook call.
The Teams URL is the webhook endpoint.





How webhooks appear in frontend development

Webhooks are used in web applications, but they are usually handled by the backend, not directly by the browser frontend.

Suppose you are developing an e-commerce website.

Frontend
Customer clicks Pay
        ↓
Backend creates Stripe payment
        ↓
Stripe processes payment
        ↓
Stripe sends webhook to backend
        ↓
Backend updates database
        ↓
Frontend displays paid status

The frontend may initiate the process, but the webhook normally goes to the backend.

Why not send Stripe webhooks directly to React?

Because a frontend application:

may not be open when the event occurs;
does not have a permanent public server endpoint;
cannot safely store webhook secrets;
can be manipulated by the user;
should not be trusted for payment confirmation.

Therefore:

Wrong:
Stripe → React browser

Correct:
Stripe → Backend webhook endpoint → Database → React frontend





opencode has hooks, though they work differently from Claude Code's /hooks. 
In opencode, hooks are provided by plugins (not a standalone hook config key).
In opencode.json, you register plugins, and plugins return hooks: "plugin": ["./.opencode/plugin/my-plugin.ts"]

Key differences from Claude Code:
- Hooks aren't declared as a config array; they're JS/TS callbacks from a plugin.
- You add behavioral hooks (tool/command/chat/permission). 
- Claude Code's hook events like PreToolUse/PostToolUse map to tool.execute.before/tool.execute.after.
- Hooks are auto-discovered from any *.ts/*.js in .opencode/plugin/ or .opencode/plugins/, or registered explicitly via the plugin array.
- There's no hook key in opencode.json that lists hook scripts directly.
To hook a specific event in your project, create a plugin file (e.g. .opencode/plugin/mine.ts) and it'll load automatically — but remember to restart opencode afterward since config isn't hot-reloaded.
